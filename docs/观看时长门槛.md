# 观看时长门槛：为什么「上报成功」却「状态不变」

> 2026-10-15 定位并修复。本文记录完整证据链，包括三条被证伪的假设。

## 现象

跑任务引擎任务时，日志出现成对的两行：

```
任务点完成: [视频] 非线性回归分析（SPSS） — 已上报500秒观看进度
WARNING - 任务点 [视频] 非线性回归分析（SPSS） 提交成功但状态仍为未完成
```

上报接口返回的是 `{"code":200,"result":true,"message":"success"}` —— **HTTP 层完全成功**，
但复查 `isFinish` 仍是 `false`。

## 结论（先说答案）

平台任务点的完成判据里，除了「读完/看完」之外还有一条**累计观看时长**：

```
score.totalTime  >=  watchDuration × 60000
   毫秒              分钟（浮点）
```

而 `totalTime` **只按真实经过的墙上时钟累计**。跳播、大跳 `currentTime`、几秒内连发心跳，
**一分一秒都不计入**。上报接口返回 `result:true` 只代表「这次打点被受理了」，不代表时长入账。

所以修复方向不是「换个接口」，而是**老老实实按真实时间播完**。

## 证据链

### 一、字段级对比：唯一有判别力的差异

`_diff_full.py` 把两个任务点的完整 JSON（`getPlanDataByGroupId` 返回的 38 个顶层键）
压平成 234 个叶子逐一对齐：

| | 时间序列（完成） | logistic模型参数求解（未完成） |
| --- | --- | --- |
| planId | 8785740 | 8360000 |
| `planUser.finish` | **1** | **0** |
| `enableDocumentWatchDuration` | **0** | **1** |
| `documentWatchDuration` | `null` | **5.0** |
| `enableCompleteRead` | 1 | 1 |
| 其余 130+ 个 `enable*` | 全 0 | 全 0（**完全相同**） |
| `conditionGroupVoList` / `tag` / `planAllowStudyCondition` | null / null / "" | null / null / "" |

`score` 对象里两边只有 `id` / `planId` / `moocDataCreateTime` 不同 —— 但那是**同一次读取**
的对比。放大到全库才看到 `totalTime` 的差别。

### 二、全账号相关性：零例外

`_watch_corr.py` 扫 27 门课 220 个任务点：

```

时长要求=无   完成=95   未完成=110  (共 205)
```

**15 个设了时长要求的任务点里 14 个未完成（93%）**，唯一例外 `6797876` 恰好是
`totalTime` 超线 4 秒的那个。反向看：不设时长要求的 205 个里有 95 个已完成 —— 说明
「未完成」不是这批任务的普遍状态，而是时长要求的直接后果。

### 四、三条受控实验：什么才算数

对 `8359997`（要求 5.0 分钟 = 300000ms）做的实验：

| # | 做法 | 墙上用时 | `totalTime` 增量 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | `report(0,0)` → 不等待 → `report(duration,2)` | ~0.3s | 0 | **跳播不给分** |
| 2 | 7 次连发心跳，`current` 从 0 跳到 60（不 sleep） | 0.35s | 0 | **连发不给分** |
| 3 | 每 6 秒一次心跳，`current` 跟随墙上时钟递增 ×7 | 45.5s | **39000ms** | **按真实间隔计入** |

再对 `8359996`（要求 13 分钟）做的定标：

| 实验 | 墙上 | `totalTime` 增量 | 倍率 | 结论 |
| --- | --- | --- | --- | --- |
| 大跳 `current=1500`（墙上 6s） | 6.1s | 0 | 0.00x | 大跳不给分 |
| 真实 6s 心跳 ×7 | 42.6s | +74.0s | 1.74x | 持续结算，**不需要发 `status=2` 触发** |
| 10 倍速节奏（墙上 6s / `current` +60） | 63.8s | +18.0s | **0.28x** | 加速**被折扣**，不能用 |
| 1x 节奏 | ~36s | +12.0s | 0.21x | — |
| 3x 节奏 | ~36s | +36.0s | **0.63x** | 3 倍速可压到约 1/3 的等待 |

> 倍率不是精确 1.0 是正常的：心跳有粒度（6 秒一次），服务端只在收到心跳时结算一次
> 间隔；且回读本身有滞后。

### 五、因果终证

`_exp_proof.py` 对 `8359997` 按真实时钟补足差额：

```
基线:  isFinish=False   totalTime=64000ms (64s)
要求:  5.0 分钟 = 300000ms，还差 236000ms → 真实播放 236 秒
结果:  isFinish=True    totalTime=304000ms (304s)   墙上共 241.3s
```

**越过 300000ms 的瞬间 `isFinish` 由 False 翻成 True。** 因果闭环，客户端没有 bug。

## 文档侧：为什么修不了

文档（planType 11）的时长走的是另一条通道，纯 HTTP 无法复现。

`task.chaoxing.com/documentStudy/learnPage` 只是一个**外壳**，真正的阅读器在独立域名
iframe 里：

```
https://pan-yz.chaoxing.com/screen/v2/file_<objectId>?…&ext={"rwyq_doc":<EPU>,"pId":<planId>,…}
```

外壳页（`_docpage.html`）里只有两个 `requestGet`：

```js
const readEnd = () => {
  if (readEndStatus.value) { console.log("readEnd"); }
  else {
    readEndStatus.value = true;
    requestGet({ encryPlanUserId }, '/documentStudy/readEnd');
  }
};
const messageListener = () => {
  window.addEventListener('message', (event) => {
    if (event.data.isFinished === 1) { readEnd(); }
  });
};
```

**没有任何时长上报调用。** 阅读器（`_panpage.html`）滚到底部时
`parent.postMessage({isFinished:1}, '*')`，外壳收到才调 `readEnd`。

实测：

| 做法 | 结果 |
| --- | --- |
| `learnPage` → 真等 40 秒 → `readEnd` | `{"result":true}`，`totalTime` 仍 `None` |
| 再连打 3 次 `readEnd`（间隔 12 秒） | `totalTime` 仍 `None` |
| `GET /documentStudy/dataLog/1/1/1` | **404** |
| `GET /documentStudy/readStart` | **404** |
| `GET /documentStudy/readLog` | **404** |
| `GET /documentStudy/lastCurrentTime/1` | **404** |

阅读器引用的 `addPoint.js`（jsjiami.com.v5 混淆，97 KB）里唯一可读的完整 URL 是：

```
https://data-xxt.aichaoxing.com/analysis/ac_mark?
```

跨域埋点，属 `aichaoxing.com` 而非 `chaoxing.com`，参数在混淆代码里。**纯 HTTP 补不上
文档的 `totalTime`。**

因此 `handle_document` 在这种情况下**如实返回失败**：

> 已上报「文档阅读完成」（阅读进度 100%），但该任务点还要求累计阅读 N 分钟；服务端当前
> 只记了 M 秒。文档时长由云盘阅读器（pan-yz.chaoxing.com）的跨域埋点另行上报，纯 HTTP
> 无法复现 —— 请在浏览器里打开该文档并停留阅读，或改用「重做模式」在浏览器中完成。

## 修复

`api/fanya_task.py`：

1. **新增** `watch_duration_ms(extra, kind) -> int` —— 读 `planBreakthroughSet` 里的
   `enableVideoWatchDuration` / `enableDocumentWatchDuration` / `enableAudioWatchDuration`
   与对应 `*WatchDuration`，换算成毫秒；没设要求返回 0。
2. **新增** `watched_ms(score) -> int` —— 从 `score.totalTime` 取值。
3. **新增** `_satisfy_watch_duration(...)` —— 按真实墙上时钟心跳，每 30 秒回读进度，
   达标后收尾并轮询 `isFinish`。三个失败出口都诚实（用户中断 / 超时预算 / 读不到计数）。
4. **`_handle_play` 新增第 0 步分支**：`required_ms > 0` 时**直接**走时长补足路径，
   不再先试「一次到位」再等被拒（服务端**总是**返回 `result:true`，等被拒的分支
   永远不会触发 —— 这正是原 bug）。
5. **`handle_document`** 改为在时长不够时返回失败 + 说明。

### 修复前后的行为

| | 修复前 | 修复后 |
| --- | --- | --- |
| 设了时长要求的视频 | 报 `result:true` → 打 WARNING「提交成功但状态仍为未完成」，函数**算成功** | 按真实时间补足 `totalTime` → 达标后收尾 → 真的完成 |
| 没设时长要求的视频 | 一次到位上报 → 真的完成 | **不变**（仍是快路径） |
| 设了时长要求的文档 | 报 `readEnd` 成功 → 打同样 WARNING，函数**算成功** | **如实返回失败** + 说明为什么纯 HTTP 做不到 |
| 没设时长要求的文档 | `readEnd` → 真的完成 | **不变** |

## 集成测试

`_it_play.py`（对象 `8359996`，故意给 100 秒小预算，走生产代码路径）：

```
要求累计观看: 780000 ms = 13 分钟
[before] isFinish=False  totalTime=264000 (264s)
  累计观看进度：服务端 264 秒 / 要求 780 秒
  累计观看进度：服务端 294 秒 / 要求 780 秒
  累计观看进度：服务端 294 秒 / 要求 780 秒
--- 墙上 106.6 秒 ---
  ok  = False
  msg = 超过单任务点时间上限（100 秒），已累计观看约 294 秒，未达 13 分钟
[after] isFinish=False  totalTime=349000 (349s)
★ totalTime 增量 = 85000ms = 85s
```

四项断言全过：走到了新分支 / 没有假称成功 / 服务端计数确实在涨 / 返回了诚实的失败信息。

> 注意服务端回读**有滞后**（上面连续两次读到 294），所以不能靠单次回读判断是否达标，
> 也不能把「读到的值」当成实时值。

## 相关选项

`ctx.options`（沿用原有键名，无需新增配置项）：

| 键 | 含义 | 默认 |
| --- | --- | --- |
| `video_heartbeat` | 心跳间隔（秒） | `6.0` |
| `video_speed` | 播放倍速（服务端按约 0.63 折算 3 倍速） | `1.0` |
| `video_max_seconds` | 单个任务点的时间上限（秒） | `7200.0` |
| `stop_event` | 中断信号 | — |

**代价提醒**：时长门槛是**真实等待**，13 分钟的要求就要 13 分钟（3 倍速约 4~5 分钟）。
这是平台的判据，没有捷径 —— 三条「捷径」假设（跳播 / 连发 / 倍速）全部被实验证伪。
