# 浏览器通道：补齐「累计阅读时长」门槛

> 这篇文章记录 2026-10-15 的一次完整逆向：**为什么文档的累计阅读时长纯 HTTP
> 补不了**，以及**用真实浏览器怎么补上**。所有结论都来自受控实验，命令可复现。

## 1. 问题：上报成功，`isFinish` 却是 false

日志里会出现这种自相矛盾的两行：

```
任务点完成: [视频] 非线性回归分析（SPSS） — 已上报500秒观看进度
WARNING - 任务点 [视频] 非线性回归分析（SPSS） 提交成功但状态仍为未完成
```

不是代码 bug。任务点的完成判据里，除了「读到 / 看到」还有一个**累计时长门槛**：

| 字段（`planBreakthroughSet`） | 含义 |
|---|---|
| `enableVideoWatchDuration` / `videoWatchDuration` | 视频要求累计观看 N **分钟** |
| `enableDocumentWatchDuration` / `documentWatchDuration` | 文档要求累计阅读 N **分钟** |
| `enableAudioWatchDuration` / `audioWatchDuration` | 音频要求累计播放 N **分钟** |

服务端把累计时长记在 `score.totalTime`（**毫秒**），判据是：

```
totalTime >= watchDuration × 60000
```

`planBreakthroughSet` 里其余 `enable*` 开关在本账号 220 个任务点样本上**全是 0**
—— 这个时长门槛是唯一有判别力的条件。

### 全账号相关性（27 门课 / 220 个任务点）

```
时长要求 = 有 → 完成 1  / 未完成 14   (共 15)
时长要求 = 无 → 完成 95 / 未完成 110  (共 205)
```

设了时长的 15 个里 14 个未完成。唯一完成的那个（`planId=6797876`）恰好
`totalTime=304000ms ≥ 5.0min×60000=300000ms`，超了 4 秒。

## 2. 关键区分：`totalTime` 只认真实经过的时间

### 视频：可以用 HTTP 真实等待

`GET {TASK_DOMAIN}/videoDataLog/dataLog/{duration}/{current}/{status}?encryId=...`
（`status`：0=播放，1=心跳，2=结束）

三组受控实验（对象 `planId=8359997`，阈值 5.0 分钟 = 300000ms）：

| 实验 | 做法 | `totalTime` 增量 |
|---|---|---|
| 一次性跳片尾 | `report(0,0)` → `report(duration,2)` | **0** |
| 快速连发心跳 | 不 sleep，`current` 0→60 连发 7 次 | **0** |
| 真实等待 | 每 6 秒一次心跳，墙上 42.6 秒 | **+74000ms** |

倍速会被采信但有折扣：同样墙上 ~36 秒，1x 记 +12000ms，3x 记 +36000ms
（约 0.63 倍）。**跳到片尾、快进、连发心跳全部计 0。**

所以视频/音频的门槛由 `api/fanya_task._satisfy_watch_duration()` 纯 HTTP 完成：
按真实节奏发心跳，定期回读，直到 `totalTime` 越过阈值。

### 文档：HTTP 完全做不到

`POST/GET {TASK_DOMAIN}/documentStudy/readEnd?encryPlanUserId=...` 返回
`{"code":200,"result":true,"message":"success"}`，确实会把
`completeWeightRate` 置成 100.0（「读完」）—— **但一分一秒都不计入 `totalTime`**：

| 实验 | `totalTime` |
|---|---|
| 调 1 次 `readEnd` | 仍为 `None` / `0` |
| 打开 `learnPage` → 真等 40 秒 → 调 `readEnd` | 仍为 `None` / `0` |
| 间隔 12 秒连调 3 次 `readEnd` | 仍为 `None` / `0` |

`documentStudy` 下也没有时长端点，4 个候选**全部 404**：

```
documentStudy/dataLog/1/1/1   → 404 {"status":404,"error":"Not Found"}
documentStudy/readStart       → 404
documentStudy/readLog         → 404
documentStudy/lastCurrentTime/1 → 404
```

### 文档时长的真实通道：云盘阅读器 iframe

`task.chaoxing.com/documentStudy/learnPage` 只是个**外壳**，正文渲染在独立域的
iframe 里：`pan-yz.chaoxing.com/screen/v2/file_<objectId>?appid=&nonce=&timestamp=&ext=&signature=`。

阅读器自己的完成判定是**滚到底部**：

```js
var scrollBottom = scrollHeight - (scrollTop + windowHeight);
var tolerance = 40;
if (!isFinishedSent && scrollBottom <= tolerance) {
    if (parent != self) { parent.postMessage({isFinished: 1}, '*'); }
    isFinishedSent = true;
}
```

外层收到 `isFinished===1` 才去调 `readEnd`：

```js
window.addEventListener('message', function (event) {
    if (event.data.isFinished === 1) { readEnd(); }
})
```

**所以「调过 readEnd」不等于「真读过」** —— 时长是阅读器按停留时间另走一条
跨域埋点算的。

### 埋点不可重放（决定性否定）

阅读器经 `addPoint.js`（jsjiami 混淆）向跨域打点：

```
GET https://data-xxt.aichaoxing.com/analysis/ac_mark?
    f=readPoint&u=<puid>&d=<JSON>&t=<时间戳>&enc=<签名>
```

`d` 解出来是：

```json
{"r":"<objectId>","t":"doc","l":1,"f":4,"p":1,"tp":1,
 "wc":22,"ic":7,"v":2,"s":<序号>,"h":<停留毫秒>,
 "ext":"{\"rwyq_doc\":<planUserId>,\"pId\":<planId>,\"oId\":\"<objectId>\",\"mrId\":0}"}
```

用 Playwright 抓下真实 URL 后做重放实验，三种都让 `totalTime` **Δ=0**：

| 重放方式 | 结果 |
|---|---|
| 原样重发（带正确的 `enc` 签名） | HTTP 200 空响应，Δ=0 |
| 篡改 `enc` 为 32 个 0 | HTTP 200 空响应，Δ=0 |
| 伪造 `h=60000`（一次报 60 秒停留） | HTTP 200 空响应，Δ=0 |

它是 **fire-and-forget 的统计埋点**，不做计分。**纯 HTTP 复现文档时长这条路被证伪。**

## 3. 解法：浏览器通道

`totalTime` 必须由**真实浏览器里的真实阅读**产生。于是新增
`api/fanya_browser.py`，用 Playwright 驱动本机 Edge：

1. 把 requests session 的 cookie 注入浏览器 context；
2. 打开 `documentStudy/learnPage?encryPlanUserId=<EPU>`；
3. 等 `pan-yz` 阅读器 iframe 加载；
4. 循环把 iframe 滚到底部（触发 `postMessage({isFinished:1})` → `readEnd`）；
5. 每 10 秒从 **HTTP 侧**回读 `isFinish / totalTime / cwr`；
6. 观测到 `isFinish=True` 才返回成功。

### 验收（真实执行，`planId=8360000`「logistic模型参数求解」）

阈值 5.0 分钟 = 300000ms：

```
[before] isFinish=False totalTime=290000 (290.0s) cwr=100.0
  t=  19.0s  totalTime= 290000 ( 290.0s)  isFinish=False
  t=  31.3s  totalTime= 300000 ( 300.0s)  isFinish=True
[after ] isFinish=True totalTime=300000 (300.0s) cwr=100.0
★ 达标 = True    ★ isFinish 翻转 = True    ★ 耗时 32s
```

同一通道另一次运行把 `totalTime` 从 0 一路推到 255000 → 285000 → 290000，
与请求日志对齐后可见：**滚到底 + `readEnd` 之后 `totalTime` 才跳变**
（`ac_mark` 每 10 秒一次但从不引起跳变）。

## 4. 部署注意（两个真实的坑）

### 坑 1：cookie 的 domain 是空串

`requests` 的 `RequestsCookieJar` 里，从 `cookies.txt` 载入的 cookie
`domain` 常常是**空字符串**。Playwright 会把它当 host-only，
`passport2.chaoxing.com` 收不到 → 被重定向到登录页（页面标题变成「用户登录」）。

必须显式改写成 `.chaoxing.com`：

```python
{"name": c.name, "value": c.value,
 "domain": ".chaoxing.com",          # ← 关键
 "path": c.path or "/", ...}
```

这与之前 CDP `Network.setCookie` 的经验一致。

### 坑 2：`%TEMP%` 不可写

Playwright 启动浏览器时会在 `%TEMP%` 下 `mkdtemp`。在本机的沙箱里该目录不可写，
表现为启动直接失败。解法是在**导入 playwright 之前**把三个变量指到工作区内：

```python
for key in ("TEMP", "TMP", "TMPDIR"):
    os.environ[key] = tmp          # 默认 <项目根>/_pw_tmp
```

可用 `FANYA_BROWSER_TMP` 覆盖。

## 7. 这套通道还能用在哪

浏览器通道解决的是**「需要真实交互/真实时间才有副作用」**这一类问题。
目前另一个候选是 AI剧情（`type=7`）：它的完成判据里也有「分数达到 90 分」，
而评分要求**智能体的回复正文**出现在对话记录里 —— 而那段正文只存在于
WebSocket 的音频转写流里。`api/fanya_story.py` 已把纯 HTTP 部分打通
（`answer/init` 重开章节、`add-chat` 发言、`host-agent` SSE 驱动、
`answer/submit` 交卷、`evaluate/stream` 评分），剩下这一环可以复用同一套
浏览器能力。

## 8. 能不能「快进」或「伪造」（2026-10-16 六组受控实验）

对象：`planId=8359999`「Logistic模型理论部分自学讲义」，要求 10 分钟
（`enableDocumentWatchDuration=1`、`documentWatchDuration=10` → 600000ms）。

| 实验 | 做法 | 结果 |
|---|---|---|
| 伪造 `readEnd` | 连发 4 次 `documentStudy/readEnd` | Δ=**0** |
| 回拨 `timestamp` | 阅读器 iframe URL 的 `timestamp` 减 1800 秒（签名仍有效、页面照常打开） | Δ=**0** |
| 反复重进阅读器 | 8 轮「重新加载 learnPage + 密集滚 190 次」，墙上 200.7 秒 | Δ=+13000ms（0.06×） |
| `ac_mark` 重放 | 原样 / `enc` 清零 / `h=60000` | HTTP 200 空体，Δ=**0** |
| 滚动密度 | 静置 25s / 稀疏（每 5s）/ 密集（每 100ms 并滚到底）/ 空切换（reload） | +7000 / +0 / **+35000** / +0 ms |
| 多开会话 | 同一个 `planId` 同时开 **4 个**阅读页，各密集滚 30 秒 | Δ=+27000ms（若按会话相加应为 +120000ms，而且文档当场就该达标） |

`ac_mark` 解码（`data-xxt.aichaoxing.com/analysis/ac_mark`）：

```
f=readPoint&u=<puid>&d={"r":<objectId>,"t":"doc","l":1,"f":4,"p":1,"tp":1,
  "wc":22,"ic":7,"v":2,"s":<序号>,"h":<阅读器自算停留毫秒>,
  "ext":"{\"rwyq_doc\":…,\"pId\":…,\"oId\":…,\"mrId\":0}"}&t=<ts>&enc=<sig>
```

`h` 与最终入账同量级（实测 720 → 8820 → 11196ms），但**结清之后**用同一个 `h`
重复发送不再引起跳变 → 它只是阅读器自报的停留时长，服务端另有结算。

结论（已写进 `docs/FRONTEND_API.md` 的 `options.concurrency`）：

1. 文档的累计阅读时长**只能靠真实阅读行为**拿到，服务端按真实经过时间结算，
   没有可用的伪造入口；
2. **多开会话不会让它变快**（不是每个会话各加一份）；
3. 把「滚到新内容」做到机器极限（每 100ms 滚一屏）时入账约 1.0–1.4× 真实时间，
   所以 10 分钟的文档最短也要 ~7–10 分钟真实时间；静置、原地滚、滚到底之后
   继续滚都不再计入（同一次实验里单页密集滚 30 秒的 Δ=0，就是因为已经滚到底）；
4. 唯一有效的「快进」手段是**并行**：让这个文档占住一个 worker，其余任务点在
   别的 worker 上同时跑完。

复现脚本（仓库根目录，`_*` 已被 `.gitignore` 忽略）：
`_probe_doc_credit.py`（readEnd / 回拨 timestamp / 已读重入）、

## 9. 实现要点：怎么把「只能真读」这件事做到最好（2026-10-16 修正）

§8 的结论是「不能伪造」，但第一版实现还踩了一个坑：**滚到底之后继续空转**
（`scrollTo(bottom)` 循环 + 10 秒轮询）。实测这样滚到底后回读会一直是同一个
数字（本次实测 599 秒卡了 3 轮 ≈ 36 秒、Δ0），而任务的单任务点预算默认
1800 秒，于是「能读」的文档也会一路空转到失败。现在的做法：

1. **滚动铺满整轮**：每轮 12 次 `scrollBy(0, 900)`、每次间隔 900ms
   （`scroll_steps` / `scroll_step_ms` / `scroll_px` 可调），而不是一次跳到底
   再干等 —— 一次到底之后剩下的等待时间一分都不记（§8 的「静置 Δ0」）。
2. **停滞即重开阅读页**：连续 `stall_rounds_limit`（默认 2）轮回读没有新增就
   重新加载学习页、回到文首重新读。重开会开始一个新的阅读会话、触发下一段
   结算（实测每轮 +15 秒左右）；`max_reopens`（默认 12）封顶。
3. **可被停止**：`should_stop` 回调在每轮循环开头检查。在此之前界面的「停止」
   只能在**任务点之间**生效，一个 30 分钟的文档会把「正在停止…」一起卡住
   （用户实测遇到的正是这个）。

真机验证（`planId=8359999`，要求 10 分钟，浏览器通道：

| 时间 | 事件 |
|---|---|
| 0.2s | `[before] totalTime=580000 isFinish=False`，转入浏览器通道 |
| 30.0s | 580 → **599 秒**（滚动铺开带来的入账） |
| 74.6s | 连续 3 轮回读无新增 → **重开阅读页（第 1/12 次）** |
| 103.3s | **614 秒、`isFinish=True`** |

结论：**这个文档被真正做完了**（104 秒，含一次重开）。带门槛的文档以前只会
空转到预算耗尽，现在能收口。入账速率约 **0.5×** 真实时间（本次两段分别为
+19 秒/40 秒、+15 秒/29 秒），所以一个要求 N 分钟的文档大约要 N/0.5 分钟
（并行的意义在这里：它占住一个 worker 时，其它任务点在别的 worker 上照常完成）。
